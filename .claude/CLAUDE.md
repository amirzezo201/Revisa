# Revisa: Rails + Inertia/React (37signals spirit)

Revisa is a content versioning and review tool. An SEO team uploads Word docs
or edits pages in the app, every save makes an immutable revision, clients
review and approve, and the approved copy gets built into WordPress by hand.
The source of truth for the domain, permissions and phases is
`docs/plans/content-versioning.md`. Read it before you do any feature work.

## Tech Stack

- **Ruby** 4.0, **Rails** 8.1, **SQLite**
- **Frontend:** Inertia Rails + React 19 + TypeScript, Vite (`vite_rails`), Tailwind v4
- **UI kit:** shadcn-style components built on `@base-ui/react` in `app/frontend/components/ui` (not Radix)
- **Routes in JS:** `js-routes` gives you `@/routes` helpers (`dashboardPath()`, `settingsProfilePath()`). Regenerate them with `bin/rails js:routes` after you change routes
- **Serialization:** Alba resources in `app/resources`. Typelizer is **not** installed, so TS types are written by hand in `app/frontend/types`
- **Auth:** Rails 8 generated auth (`has_secure_password` + `Session`), `Current.session` / `Current.user`. No Devise
- **Authorization:** Pundit + Permission/Role/Ownership (see `.claude/rules/authorization.md`)
- **Background:** Solid Queue | **Cache:** Solid Cache | **WebSockets:** Solid Cable
- **Testing:** Minitest + fixtures (no RSpec, no FactoryBot), with the `inertia_rails` Minitest assertions
- **Lint:** RuboCop (omakase) for Ruby, Biome for TS/TSX, `tsc` for types. Package manager: **pnpm**
- **Deploy:** Kamal 2 + Thruster

## Architecture

```
app/
  controllers/        # Thin, CRUD only, inherit InertiaController. authorize / policy_scope in every action
  models/             # Rich domain models + POROs (Revision::Import, Revision::Diff)
  models/concerns/    # Horizontal behavior (Role::Templates, Eventable, ...)
  policies/           # Pundit policies. ApplicationPolicy maps actions to "resource.action" permissions
  resources/          # Alba serializers that feed Inertia props
  jobs/               # Shallow. They call model methods (_later/_now)
  mailers/            # Minimal, plain text first. Called from jobs
  frontend/
    pages/            # Inertia pages: pages/<controller path>/<action>.tsx
    components/ui/    # base-ui/shadcn primitives (Button, Field, Input, Dialog, ...)
    components/       # App components (breadcrumbs, nav, settings-section, ...)
    layouts/          # AppLayout (with breadcrumbs), SettingsLayout, AuthLayout
    lib/              # utils, permissions.ts (can/canAny, resourceLabels, AREAS, impliedViewIds)
    hooks/            # use-can (useCan), use-flash, use-clipboard, ...
    types/            # Hand-written TS types matching the Alba resources + SharedProps
    routes.js         # Generated by js-routes. Never edit by hand
```

No `app/services/`, `app/queries/` or `app/forms/`. Domain logic lives in models
and POROs under `app/models` (for example `Revision::Diff`).

## Core Philosophy

- **Vanilla Rails:** rich domain models, thin controllers. Service objects only when clearly justified
- **Everything is CRUD:** state changes are new resources (`POST /revisions/:id/submission`, not `#submit`)
- **State as records:** no boolean flags for business state. `Submission`, `Review`, `Resolution` and `Publication` are records
- **Derived status:** `Page#status` is computed from records and never stored
- **Immutable history:** revisions are never updated. Corrections create a new revision
- **Concerns for organization:** focused, single-purpose concerns
- **Current for context:** `Current.session`, `Current.user`
- **Shallow jobs:** `_later` / `_now` pairs. The job calls a model method and the logic stays in the model
- **Server is the gate:** the frontend hides buttons with `useCan()`, but the server always enforces the rule with Pundit. Every action calls `authorize`; controllers with nothing to authorize declare `skip_authorization_check`

## Deliberate deviations from the 37signals template

| Template says | Revisa does | Why |
|---|---|---|
| Hotwire (Turbo + Stimulus), Importmap, ERB views | **Inertia + React + Vite**, pages in `app/frontend/pages` | Starter kit and richer editor/diff UI |
| No Pundit; roles on User | **Pundit** + Permission/Role/RolePermission/UserPermission/Ownership | Owner-configurable roles; clients log in with restricted access |
| UUIDv7 primary keys | **Integer IDs** | No enumeration risk because every lookup goes through `policy_scope` |
| `account_id` on every table, URL tenancy | **No `account_id`, no multi-tenancy** | One team. Clients are isolated by `SiteAccess` + `*_own` permissions |
| Passkeys / magic links | **Password auth** (Rails 8 generator) | Starter kit default. Users are invited by the owner |
| No foreign key constraints | **Same: no FK constraints** (`foreign_key: false`). Unique indexes enforce invariants | Kept from the template |

## Domain glossary

See the `revisa-domain` skill for invariants and the model map.

- **Site:** one client website. Holds pages.
- **SiteAccess:** user ↔ site pair. Decides which sites a user with only `*_own` permissions (for example a client) can see.
- **Page:** a content piece on a site (title, slug, target keyword, page type, live URL).
- **Draft:** the one mutable, autosaved working copy of a page. `base_revision_id` detects conflicts.
- **Revision:** an immutable numbered snapshot (v1, v2, ...) of a page's sections and meta. Its `source` is `upload` / `editor` / `restore`. It may have the original `.docx` attached.
- **Section:** `{ key, kind, heading, body_html }` inside a draft or revision. The stable `key` makes diffs line up.
- **Submission:** a state record saying "this revision is up for review".
- **Review:** a verdict on a revision (`approved` / `changes_requested`). One approval approves the revision.
- **Comment:** feedback anchored to a section of a revision. `internal` comments are hidden from clients.
- **Resolution:** a state record saying "this comment is resolved".
- **Publication:** the manual record "revision vN was built into WordPress at <url>".
- **Event:** a timeline entry (`eventable` polymorphic, `action`, `particulars`).
- **Permission:** `resource.action` (for example `pages.update`). **Role** bundles permissions, **UserPermission** adds direct grants, and **Ownership** marks the single owner who bypasses all checks.

## Key Commands

```bash
bin/setup                                   # Initial setup
bin/dev                                     # Rails + Vite dev servers
bin/rails test                              # Full test suite
bin/rails test test/models/page_test.rb:14  # Single test
bin/rails test:system                       # System tests
bin/ci                                      # Full CI (rubocop, biome, tsc, routes, audits, brakeman, tests)
bin/rubocop -a                              # Auto-fix Ruby style
pnpm lint                                   # Biome (lint + format check); pnpm lint:fix to fix
pnpm check                                  # TypeScript type check
bin/rails js:routes                         # Regenerate app/frontend/routes.js + routes.d.ts
bin/rails db:migrate
bin/rails permissions:seed                  # Sync Permission::CATALOGUE into the DB (safe to re-run)
bin/rails permissions:seed_roles            # Create roles from Role::Templates (Admin re-synced; curated roles untouched)
bin/rails permissions:cleanup_obsolete      # Delete permissions no longer in the catalogue
bin/rails "permissions:make_owner[email]"   # Make a user the owner
```

## Development Workflow

1. Write a failing Minitest test with fixtures (model, policy, controller)
2. Implement the minimal code to make it pass
3. Refactor while the tests stay green
4. Before finishing: `bin/rails test`, `bin/rubocop`, `pnpm lint`, `pnpm check`

For a full feature slice (route → policy → controller → resource → TS type → page → test), use the `inertia-feature` skill. For anything touching permissions, use the `permissions` skill.

## Naming Conventions

| Layer | Pattern | Example |
|-------|---------|---------|
| Model | Singular PascalCase | `Revision`, `SiteAccess` |
| Controller | Plural, nested by resource | `Revisions::SubmissionsController`, `Pages::ImportsController` |
| State record | Noun describing state | `Submission`, `Resolution`, `Publication` |
| Policy | `<Model>Policy` | `PagePolicy`, `ReviewPolicy` |
| Resource | `<Model>Resource` | `RevisionResource` |
| Page | `app/frontend/pages/<controller path>/<action>.tsx` | `pages/pages/revisions/index.tsx` |
| Concern | Adjective / -able | `Eventable`, `Versionable` |
| Job | `Model::VerbJob` | `Submission::NotifyJob` |
| Test | `ModelTest` / `ControllerTest` / `PolicyTest` | `Revisions::ReviewsControllerTest`, `PagePolicyTest` |

## Style Guide (37signals)

- Expanded conditionals over guard clauses (exception: single-line early returns at the start of a method)
- Method ordering: class methods > public instance methods (`initialize` first) > private
- Order private methods by invocation flow (call order)
- Bang methods (`!`) only when a non-bang counterpart exists
- No newline under `private`/`protected`. Indent the content under it
- `belongs_to :author, class_name: "User", default: -> { Current.user }` for context defaults
- `touch: true` on child associations where a parent's cache depends on them
- TS/TSX: follow Biome (double quotes, no semicolons), `@/` imports, function components, no `useEffect` + fetch for page data (use props)

See @../docs/rails-development-principles.md for full development principles.
